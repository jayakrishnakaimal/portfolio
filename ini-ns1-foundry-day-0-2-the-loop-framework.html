INI + NS1 Foundry: Day 0–2 & The Loop Framework

Exploring integration between IBM Network Intelligence, NS1 Foundry, SevOne, watsonx Orchestrate & Concert
Background: The NS1 Foundry team (already in conversation with SevOne) is exploring how their product and IBM Network Intelligence (INI) can work together. The key questions center on delta analysis between the two products, how data and agent interactions can be structured across a lifecycle, and where watsonx Orchestrate agents and watsonx.gov fit into the flow. This document frames the exploration across a Day 0/1/2 model and a dual concurrent loop model.

"The Loop" — Two Concurrent Tracks

Rather than a purely linear Day 0→1→2 progression, two parallel loops run concurrently once the environment is live. Each loop has its own cadence and connects back to shared systems.

Track A — Network Operations Loop
1
Design — Model network topology, DDI schema, traffic policies
NS1 Foundry, INI (Day 0)
↓
2
Connect & Test — Provision and validate live network through INI
INI, SevOne collectors (Day 1)
↓
3
Monitor & Refine — Continuous performance monitoring, anomaly surfacing
SevOne, INI dashboards (Day 2)
↓ (feeds back to Design or triggers Agent Loop)
Track B — Agentic Automation Loop
1
Detect Pattern — Persistent or recurring network aberration identified
SevOne / INI telemetry (Day 2 trigger)
↓
2
Design Agent — Define remediation workflow, guard rails, escalation rules
watsonx Orchestrate + watsonx.gov (Day 0-style)
↓
3
Test & Deploy Agent — Validate agent in staging, publish to production
WxO agent catalog (Day 1-style)
↓
4
Automate & Track — Agent acts; results logged back for audit and learning
INI, Concert, ServiceNow (Day 2 ongoing)
↓ (feeds back to Detect or closes ticket)
⟵   Both loops share INI as the network data backbone   ⟶   ·   Aberration signals in Track A trigger Track B entry

Open Questions to Explore

  • Is INI the system of record for network state, or does NS1 Foundry maintain its own authoritative DDI store? How do they reconcile?
  • Does the Day 0 design phase live entirely in NS1 Foundry, with INI serving as the provisioning + ops layer from Day 1 onward?
  • Where does watsonx.gov sit in the data pipeline — does it govern agent decisions before they execute, or audit after?
  • Should WxO agents be triggered by SevOne alerts directly, or should all triggers be routed through INI first for normalization?
  • Is Concert or ServiceNow the primary ITSM endpoint for agent-created remediation actions — or both, based on incident type?
  • What is the minimum persistent aberration threshold that should trigger Track B (agent loop) vs. a standard alert/notification?
  • How does NS1 Foundry's advanced traffic steering (Anycast, filter chains) map to INI's current traffic visibility model?
  • Is there a unified data schema (e.g., IPFIX, OpenTelemetry) that both INI and NS1 Foundry can emit to watsonx.gov?

Key Integration Opportunities

Design-to-Deploy Bridge
NS1 Foundry Day 0 blueprints push directly into INI as provisioning instructions, eliminating manual re-entry and drift between design intent and live state.
Persistent Anomaly → Agent
SevOne/INI telemetry identifies recurring aberrations that cross a defined threshold, automatically triggering a WxO agent design + deploy cycle (Track B).
Governed AI Operations
watsonx.gov provides auditability and policy enforcement for every AI-driven decision made by WxO agents acting on network data — critical for regulated environments.
Closed-Loop Remediation
Agent actions logged in Concert/ServiceNow feed back into INI as resolved state, creating a closed loop between detection, action, and network truth.
Unified Observability Layer
Position INI + SevOne as the shared observability plane that both NS1 Foundry and WxO agents consume — a single source of network truth for all automation.
Delta-Driven Roadmap
The capability delta between INI and NS1 Foundry reveals a natural co-sell / co-build opportunity: Foundry's design strengths + INI's ops + AI strengths = full lifecycle.
